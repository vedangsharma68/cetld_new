# TallyPrime import

Connections → TallyPrime → Import from Tally accepts UTF-8 CSV or XML (including BOM-marked UTF-16 XML), up to 2 MB and 2,000 source rows. Normalized customer/invoice data is capped at 3 MB to leave room for preview decisions; unusually large escaped fields get a clear request to export fewer rows. No dependencies are added. XLSX is unsupported; export CSV or XML instead.

Apply the `tally_import` migration with the regular release migration process before deploying this version. It adds owner-only `preview_tally` and `import_tally` RPCs and a private planner. Both actions share one HTTP endpoint, keeping the project within the Vercel Hobby function limit. This endpoint imports lightweight authentication/store modules and does not pull in OCR, image or PDF dependencies.

Preview is read-only: it checks existing workspace records, duplicate rows within the file, customer identity and email conflicts. Every customer and invoice is shown with a create, skip or fail action and a reason, plus exact per-entity totals. Invalid parsed fields block confirmation. Predictable database conflicts remain visible as failed rows; other valid rows can be imported. Nothing is saved until the owner confirms.

Confirmation re-parses the file, rebuilds the same plan under the workspace import lock, and compares its hash before inserting anything. Changed matches, currency settings or conflicts require a fresh preview (HTTP 409). The browser sends a short plan hash rather than echoing the plan, keeping a file at the cap within Vercel's request-size limit. Unexpected row failures are reported; retrying with a fresh preview skips successful rows and retries corrected failures.

CSV customers use `Name` or `Ledger Name`, plus optional `Email`, `Phone`, `GUID`, `Master ID`, `Parent`. Sales use `Invoice Number` or `Voucher Number`, `Customer`/`Customer Name`/`Party Ledger Name`/`Particulars`, `Date`/`Invoice Date`, and `Amount`/`Total Amount`/`Debit Amount`. Optional columns: `Due Date`, `Currency`, `GUID`, `Master ID`, `Voucher Type`. Headings ignore spaces and punctuation. Quoted commas, escaped quotes, embedded newlines, CRLF and UTF-8 BOM are supported. Unused GSTIN/tax fields are ignored. Non-Sales voucher types and non-Sundry Debtors ledger parents are ignored.

XML supports ledger masters and Sales vouchers in export envelopes. Customer contacts use EMAIL and LEDGERMOBILE/LEDGERPHONE. Invoice totals come from the party ledger entry, not a sales/tax ledger entry. Cancelled and optional vouchers are ignored. DTDs/entities, malformed XML, nested vouchers, ambiguous duplicate scalar fields and nesting over 64 levels are rejected. Missing required sales fields produce validation errors. Tax fields are ignored.

Dates accept YYYY-MM-DD, YYYYMMDD or DD-Mon-YYYY, from year 2000 onward. Missing due dates use the invoice date and are shown in preview. Missing currency uses the workspace currency. Explicit supported currencies (INR, USD, EUR, GBP, AED, SGD, AUD, CAD, CHF) are preserved without conversion; the preview warns about mixed or different currencies. Other currencies and ambiguous XML foreign-exchange amount expressions fail validation. Amounts must be plain numeric values with at most two decimal places.

Each sales row is one invoice; consolidate CSV line-item exports before import. Only unpaid invoice totals are imported. Payments, credit notes, opening balances, GST filing and accounting ledgers are outside this flow. Export unpaid sales invoices and review them before configuring reminders.

Customers match by Tally GUID first, then unambiguous trimmed case-insensitive name. Renamed ledgers with the same GUID resolve to the existing customer. Invoices match by Tally GUID or original invoice number plus customer; the same original number can belong to different customers. Deleted invoice identities are skipped rather than resurrected. Existing records are never overwritten.

cetld assigns its usual invoice number and preserves the Tally voucher number as `metadata.source_invoice_number`. Both entity types carry `metadata.source = tally` and `metadata.tally` with GUID, original master ID and ledger/voucher identity. Invoices carry `bookkeeping_origin = tally`; no Zoho/QuickBooks external linkage is set. They start as ordinary draft receivables using the existing reminder lifecycle. The import does not send reminders or sync bookkeeping.
